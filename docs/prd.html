轉向 ① 推播經濟學成為骨架

「什麼時候可以吵你」不是細節,它決定這產品在手機上活不活得下去。進度用編輯(安靜),要你做事才用新訊息(響)。

轉向 ② 安全從「問你」改成「硬牆 + 名單」

路徑越界直接拒、危險指令直接拒、日常指令直接跑,只有灰區才問。批准疲勞本身就是安全漏洞——問太多次,人就閉著眼按 ok。

刪掉的東西:run <專案>、sessions、use latest、new;多會話 / 歷史匯入 / ACL 角色 / 設定檔驅動全部降級。理由一致:選項愈多愈不方便。

⚠️ §0 整份設計壓在一個尚未驗證的假設上(P0)

「Teams 中編輯既有訊息不會發手機推播,新訊息會。」

成立 → 每輪推播可壓到常態 1 次。不成立 → 「持續回報」和「不吵你」直接衝突,必須改成只能 !tb status 拉取,推翻下面 §3.2 與 §5 的全部設計。

驗證方法:發一則訊息 → 手機確認推播;同一則連續編輯 3 次 → 觀察是否再推播。驗證前 §3.2 不該開工。

一個具體的下午(這就是全部目的)

六條設計原則

P1 打字量與風險成正比

安全的事 0~1 個字;只有真的會搞砸的事才要你多打字。

P2 編輯優於新訊息

新訊息會推播,是稀缺資源。進度一律就地編輯。

P3 沉默也是訊號

不刷屏,但永遠不無聲卡住;心跳讓你知道它還活著。

P4 預設就對

不指定專案 = AgentHub。幾乎不需要設定——設定項愈多愈不方便。

P5 結論優先,細節 on demand

手機預設只給一行;!tb 細節 才展開。

P6 安全邊界是硬牆,不是問答題

「絕對不行」直接拒、「絕對可以」直接跑;只有灰區才打擾你。

安全模型:兩道硬牆 + 一組名單(而不是一直問你)

出發點是便利,不是防禦。先命中先決定,不往下走:

硬牆一:路徑(不可批准)

讀或寫只要落在 D:\AgentHub 外,一律違規、直接拒絕。涵蓋 .. 跳脫、絕對路徑、UNC、symlink/junction、環境變數展開後越界——以解析後的真實路徑判定。

unlock 只切換「AgentHub 之內能不能寫」,永遠不擴大路徑範圍。

為什麼這樣更好用

這是唯一能讓你敢隨手交辦的保證。你不必在批准當下自己判斷「這個路徑安不安全」——那本來就不該是手機上做的事。

誤發的損害因此有明確天花板。

白名單(日常指令直接跑,0 打擾)

類別例
讀取/檢視ls、dir、type、cat、git status、git diff、git log
建置測試npm test、npm run <script>、npm ci、node、tsc、dotnet build/test

白名單是 per-project,由 ok 永遠 逐步長出來 → 打擾隨使用時間遞減。但白名單不能覆蓋硬牆:git commit 在白名單上,若要寫的檔在 AgentHub 外,仍然被拒。

與現有實作的落差:src/security/guards.ts 目前把破壞性/提權歸類為 always-approve(一律要問),依本節要改成 deny(直接拒) 並新增白名單比對 → roadmap R7。

推播預算(什麼時候會吵你)

每輪任務目標:常態 1 次(只有「完成」)。加上名單制後,批准那次在一般開發任務裡不會發生,≤2 次是最壞情況而非常態。

事件送法推播?
收到交辦 → ⏳ 已收到新訊息你剛發完,人在螢幕前,不算成本
進度更新(可能數十次)編輯同一則否 ← 整份設計的關鍵
心跳時間戳編輯同一則否
指令命中白名單直接跑編輯同一則否 ← 名單制買到的安靜
命中黑名單 / 路徑越界被拒編輯同一則(寫明原因)否(不必問你,所以也不必吵你)
需要你批准(僅灰區)新訊息是(少數情況)
完成 / 失敗新訊息是(常態唯一一次)
卡住警告(>5 分鐘無進展)編輯 + 一次新訊息是(例外,值得)

執行中你能插手的四件事(§3.7)

核心:一個 session 同時只有一個 active turn(queue.ts maxConcurrent=1 + per-project 鎖)。在此前提下四種臨時狀況各有明確歸屬。

你做的事系統怎麼處理引擎現況
追加說明 / 插話(純文字)turn/steer 併入當前輪,不用先停再重下(帶附件則排下一輪)引擎存在 adapter.ts:200·runner 未接
另開任務(這是別的事)排隊,不打斷當前輪;回報位置「前面還有 1 件」;同屬 AgentHub 受鎖序列化JobQueue.enqueue 回位置
緊急喊停兩級:stop=收尾停(turn/interrupt)/kill=硬停;停完問排隊的要不要清interrupt 存在·未接 → R8
排隊中反悔!tb 取消 <n> 移除未開跑的,不影響正在跑的佇列可查·取消待接

追加 vs 另開,怎麼分

預設「執行中純文字」當追加(steer);帶附件或明顯新目標則排下一件。拿不準不猜——回一句「併入當前還是另開?回 併/新」,寧可多問一次也不要污染正在跑的輪。

不打架

steer 若正等批准 → steer 文字不當批准,排到批准解決後。喊停不受推播節流影響,立刻可用;kill 是唯一保證中斷失控輪的手段。停/完成後狀態卡不再掛 ⏳。

關手機 ≠ 停止任務

任務跑在桌面 runner,手機只是遙控器。你的手機斷線→任務照跑,重連時 outbox 補送更新(reconcileOutbox)。這是常駐架構的好處:不必守著手機。

runner 崩潰才是真中斷

CDP 崩/Teams 重登/筆電休眠/帳號停權 → thread/resume 接回對話;in-flight job 標 unknown 不盲跑(可能已改一半檔,`markProcessLossUnknown`);離線窗有告知;離線一律回落 read-only。已實作於 recovery.ts。

一次清空排隊

!tb 取消 全部 / 清空 移除所有排隊(未開跑),正在跑的不受影響(要停用 stop/kill)。回報「已清除 N 件」。
