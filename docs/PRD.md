日期:2026-09-24。狀態:**設計定案中,核心體驗尚未實作**(見 §0.5 實作現況對帳)。27 task / 測試 136 passed 證明的是「單元與端到端管線能跑」,**不等於 PRD 承諾的體驗已成立**。
v2 在 git 歷史 `20c4404..7ea1bc6`。參考:`docs/architecture.md`、`docs/product-brainstorm.md`;體驗證據見附錄 A(讀 telecodex 原始碼)。

## 前言:這版跟 v2 差在哪

v2 是**功能表**——把 telecodex 有的東西逐條抄成需求 H~O,再標「已實作/規劃」。問題是:功能齊全不等於好用。一個功能全開但每分鐘推播一次的 bot,在手機上活不過三天。

v3 改成從**使用時刻**往回推:先問「這一刻使用者在做什麼、痛在哪」,再決定要什麼功能。推導出來的結果和 v2 的優先序**明顯不同**(§7)。

兩個實質轉向:

1. **推播經濟學成為骨架**(§0/§5)——「什麼時候可以吵你」不是細節,它決定這產品在手機上活不活得下去。
2. **安全從「問你」改成「硬牆 + 名單」**(§6)——v2 是「危險操作一律要問」,v3 是路徑越界**直接拒**、危險指令**直接拒**、日常指令**直接跑**,只有灰區才問。**批准疲勞本身就是安全漏洞**:問太多次,人就會閉著眼按 `ok`。

**刪掉的東西**(v2 有、v3 拿掉):`run <專案>`、`sessions`、`use latest`、`new`(§4);多會話、歷史匯入、ACL 角色、設定檔驅動全部降級(§7)。理由一致:**選項愈多愈不方便**。

## 0. 整份設計壓在一個假設上(P0,必須先驗證)

> **Teams 中「編輯既有訊息」不會發手機推播,「新訊息」會。**

如果這成立,整個體驗設計就有了骨架:**進度用編輯(安靜)、要你做事才用新訊息(響)**。每輪任務的推播預算可以壓到常態 1 次(§5)。

如果不成立(編輯也推播),那麼「長任務持續回報」和「不吵你」就是直接衝突,必須改用完全不同的策略——例如進度只存在 `!tb status` 拉取、完全不主動推。**這會推翻 §3.2 和 §5 的全部設計。**

在這件事驗證前,§3.2 不應開工。這是本版最重要的一條。

### 若賭輸了(PIVOT 備案,先寫死不等驗完)

會議指出:PRD 只寫了 GO 情境,沒給 PIVOT 的 UX,等於把最大商業風險留白。現在先定案:

- **若編輯也推播** → 預設改為**進度完全不主動推**,只在**完成 / 失敗 / 需批准**三種事件推(仍是常態 1 次)。
- 進度改由**極省打字的拉取**取得:裸 `?` 或 `s` = `!tb status`。
- 心跳、卡住警告在此情境下**不主動發**,只在你拉取時回報。
- **產品仍成立**:價值主張從「持續安靜回報」退化為「交辦 + 一次結論 + 隨手可拉」,仍勝過「跑回電腦」。這不是 no-go,是降級。

### 驗證步驟(擴充,尚未做)

1. 常駐 runner 發一則訊息到自己聊天 → 手機確認收到推播。
2. 同一則訊息連續編輯 3 次 → 手機觀察**是否再次推播**、鎖定畫面預覽是否更新。
3. **高頻編輯**:同一則訊息 60s 內編輯多次(模擬心跳頻率)→ 觀察是否累積成推播或觸發 Teams 降頻。這決定 §3.2 的「0 推播」與「心跳 ≤60s」是否天生衝突。
4. **前置 spike(RD)**:先確認 CDP **能不能**對自己剛發的訊息(`data-mid`)完成一次程式化編輯並回讀確認 —— 這比「編輯會不會推播」更前面,因為 `editMessage` 目前根本不存在(§0.5)。編輯後 `data-mid` 是否穩定也要驗(不穩→心跳定位鍵會漂移)。
5. 記錄於 `tasks/taskNNN-notification-economics/evidence/`。

## 1. 它到底解決什麼(一個具體的下午)

你在外面。想起早上那個測試還紅著。

- **14:02** 你打開 Teams 的「與自己聊天」,語音講一句:「把昨天那個型別錯誤修掉,跑一下測試」。
- **14:02** 幾秒內出現一則 `⏳ 已收到`。你把手機收起來。
- **14:03–14:13** 它跑 `git diff`、改檔、跑 `npm test`——**全在白名單,一次都沒吵你**。你在咖啡廳順手瞄一眼,那則訊息已經變成 `⏳ npm test 執行中 · 更新於 14:07:32`。
- **14:14** 手機**響第一次也是唯一一次**:「✅ 完成 · 改 1 檔 · 12 passed」。
- **19:30** 你回到電腦,在 `D:\AgentHub` 開終端機 `codex resume`——**接的是同一個 thread**,下午講過的話不用重講。

如果它中途想跑一個沒見過的指令(例如 `npx some-codemod`),才會多響一次問你,你回 `ok`,或回 `ok 永遠` 讓它以後別再問。如果它想動 `D:\AgentHub` 以外的檔,**連問都不會問,直接拒絕**(§6.1)。

這份 PRD 的全部目的,就是讓上面這 5 個時刻都不卡。

## 2. 六條設計原則

| # | 原則 | 具體含意 |
|---|---|---|
| P1 | **打字量與風險成正比** | 安全的事 0~1 個字;只有危險、只有真的會搞砸的事,才要求你多打字確認 |
| P2 | **編輯優於新訊息** | 新訊息是稀缺資源(會推播)。進度一律就地編輯 |
| P3 | **沉默也是訊號** | 不刷屏,但**永遠不無聲卡住**;心跳讓你知道它還活著 |
| P4 | **預設就對** | 不指定專案 = AgentHub;不指定參數 = 最合理的值。幾乎不需要設定 |
| P5 | **結論優先,細節 on demand** | 手機預設只給一行;`!tb 細節` 才展開 |
| P6 | **安全邊界是硬牆,不是問答題** | 「絕對不行」的事直接拒(不問)、「絕對可以」的事直接跑(不問);只有灰區才打擾你(§6) |

## 3. 六個使用時刻

每個時刻寫四件事:**現在的痛 → 設計 → 為什麼這樣方便 → 怎麼驗收**。

### 3.1 交辦的那 5 秒

**痛**:手機打字慢。要先想「這屬於哪個專案」「指令怎麼拼」更慢。

**設計**
- `!tb <自然語言>` 就是交辦,**不需要專案名**,預設 AgentHub。(已實作)
- 前綴接受 `!tb` / `@tb` / 全形 `！tb` / `＠tb`。(已實作)
- **自己聊天前綴,逃脫方向反轉**(USER 決議,§8 Q1):**預設當筆記(不送),要送才顯式加標記**——而非「預設全送、用 `.` 擋」。理由:把自己聊天當「邊想邊記」的人,漏一個標記就把私人筆記/思考噪音當指令執行,失敗模式應該是「忘了加標記=沒送」(無害)而非「默默誤執行」。免前綴預設**關**,首次使用問一次。→ **§7 R2**
- **語音交辦**:Teams 手機端按住就能錄,轉逐字。但**低可信輸入不直通高權限**(評審):轉完先**回顯逐字稿**讓你瞄一眼,含破壞性字樣或超過一定長度**強制確認再執行**;中文語音對檔名/指令/變數名易錯。先做可行性 spike(CDP 能否取得音檔/轉錄)再定,未過降回 P2。→ **§7 R3**
- **分享即交辦**:從瀏覽器/相簿分享到 Teams 自己聊天,附件落 `.teambot/inbox`,連同文字一起交辦。**經分享/附件/引用進入的內容一律標記 data-only,不當指令解析**(§6.4 信任根)。→ **§7 R4**

**為什麼方便**:把交辦成本從「解鎖 → 找對話 → 打前綴 → 想專案名 → 打完整句子」壓到「按住講一句」。

**驗收**:交辦一件事的中位輸入成本 ≤ 15 字元,或 1 則語音。

---

### 3.2 等待的那 10 分鐘 ⚠️ 依賴 §0 驗證

**痛**(兩個相反方向,這才是真正難的地方):
- 太安靜 → 「它是不是掛了?」焦慮到想跑回電腦。
- 太吵 → 手機每 20 秒震一次,第二天就把通知關掉,等於整個產品死掉。

**設計**
- 一輪只佔**一則訊息**,內容持續被覆寫(⏳ → 正在做什麼 → 結論),**用編輯,不發新訊息**。
- 更新節流:`max(900ms, 送出間隔)`,且內容沒變就不送。
- 訊息裡帶**心跳時間戳**(`更新於 14:07:32`)。這是我們版本的「正在輸入」——Teams 網頁 DOM 不適合做 typing 指示器,但一個會動的時間戳同樣能回答「它還活著嗎」。
- **心跳必須由 Codex app-server 事件驅動**(TurnStarted/ItemStarted 等的時間戳),**不是本地 `setInterval`**(評審關鍵):否則 Codex 卡死時心跳照跳=結構性說謊。心跳要能區分**三態**:活著在前進 / 活著但閒置(`仍在執行,閒置 Ns`)/ 通道已斷。
- 進行中只顯示**截斷後的第一段**;收尾才給全文。
- **卡住要說**:超過 N 分鐘沒有任何 Codex 事件 → 訊息改成 `⚠️ 已 N 分鐘無進展`,而不是繼續假裝在跑。N 預設 3 分、可設(§8 Q2)。

**為什麼方便**:你瞄一眼就知道進度,而它從頭到尾**沒有吵過你一次**。焦慮和噪音同時解決。

**驗收**:長任務期間手機推播 **0 次**;任何時刻「不確定它還活著」的時間為 0(心跳間隔 ≤ 60s)。⚠️ 兩者可能天生衝突(頻繁編輯是否被 Teams 當新活動而推播),須由 §0 步驟 3 一起量。

### 3.3 被打斷的那一刻(決策關卡)

**痛**:telecodex 按一顆按鈕就好。我們走 CDP 操作網頁版,**送不出可互動卡片**——這是硬限制。若照搬「打確認碼」,使用者要在手機上準確打出 `!tb approve a3f2`,錯一個字元就失敗。這是目前體驗最差的一環。

**最重要的一步是讓這一刻很少發生。** 經 §6 的硬牆 + 名單制之後,日常開發指令(`npm test`、`git diff`)**根本不會問你**,危險指令**直接拒也不問**——真正需要你決定的只剩「沒見過的灰區指令」。先把數量壓下來,再優化單次成本:

**設計(按打字量由少到多)**

| 情境 | 使用者要打 | 說明 |
|---|---|---|
| **只有一筆待決**(絕大多數) | `ok` / `好` / `y` / `no` | **不需要代碼**,但綁的是**你看到的那則批准訊息**(見下方競態) → **§7 R1** |
| 多筆待決 | `ok 2` | 代碼用**每對話遞增的小序號 1/2/3**,不用隨機碼——手機上好打、好念、不會看錯 |
| 這類以後都別再問 | `ok 永遠` | 把該指令樣式加進**該專案白名單**(§6,僅自己聊天),下次直接跑 |

> **裸 `ok` 競態(評審 P0,USER 標「最恐怖的失敗」)**:手機常延遲數分鐘才看到批准訊息,期間可能又冒出第二筆待決、或第一筆已逾時被自動拒。若裸 `ok` 綁「當下唯一待決」,你會**批准到一個沒看過的操作**。
> - **正解**:批准目標永遠由 **TeamBot 自維的 pending 佇列(含版本號)** 決定;新待決進來即 bump,使先前的裸 `ok` **失效並退化為回報**「這筆已變/已逾時,現在待決是 X,請回 `ok 2`」,而非默默套用。
> - **引用只帶資料,不決定批准目標**(解決 §9「引用不繼承權限」與舊版「引用反查 requestId」的矛盾)。

- 批准訊息**必須是新訊息**(要推播),且**一次只問一個問題**;前 40 字元自帶序號+一句人話(例「`#2 允許刪除 build/ 目錄?`」),確保鎖屏截斷仍可判斷。
- 等待期間,狀態卡同步改成「⏸ 等你批准 `npm test`」——讓你看得出**為什麼停住**。
- **逾時自動拒絕,永不自動批准**。TTL 需定一個值並與手機延遲中位數對齊(現況 2 分/30 分/15 分三方不一致,§0.5);逾時後訊息改成「已逾時拒絕,要重試回 `retry`」。
- **`ok` 免代碼僅限自己聊天單人前提**;群組一旦開啟,回到帶序號 / 隔離 DM 路徑(§8 Q3)。

**為什麼方便**:兩層同時壓——**次數**靠 §6 名單制壓到接近 0,**單次成本**從「11 個字元且不能打錯」壓到「2 個字元」。而 `ok 永遠` 讓打擾隨使用時間**遞減**。

**驗收**:一般開發任務全程 **0 次批准**;真要問時 ≤ 3 字元;批准訊息永遠指明「在等什麼」;狀態變動後舊的裸 `ok` 不生效。

### 3.4 拿回結果

**痛**:手機上看 diff 是酷刑。倒一大段 log 出來等於沒回報。

**設計**
- **兩段式**:第一行就是結論(`✅ 完成 · 改 1 檔 · 12 passed`),細節接在後面但**預設摺疊感**(短)。
- 結果是**新訊息**(要推播),同時把那則進度卡編輯成一行收掉,避免兩則訊息打架。
- 取權威結果只認 `final_answer`,忽略 commentary/deltas;一個 turn **冪等只回一次**。(已實作)
- 細節 on demand:`!tb 細節` / `!tb diff` / `!tb 檔案`。
- 產物(`turns/out` 下的檔案)**自動回傳**成 Teams 附件,不用你再去翻路徑。→ **§7 R4**

**為什麼方便**:鎖定畫面掃一眼就知道成不成;要細節時才花流量和注意力。

**驗收**:結論在**第一行 30 字內**可判斷成敗。

---

### 3.5 回到電腦前(這其實是最大的賣點,v2 完全沒講)

**痛**:多數「手機遙控」工具的上下文是斷的——手機上聊完,回電腦得重講一遍。

**設計**
- 因為是**同一個常駐 Codex thread** 跑在 `D:\AgentHub`,回到電腦開終端機 `codex resume` 接的就是同一段對話。**這件事現在已經成立**,只是從來沒被當成功能寫出來。
- `!tb 交接` 印出 thread id + cwd + 這輪改了哪些檔,方便直接接手。→ **§7 R5**
- 反向也成立:電腦上做到一半出門,手機接著問。

**為什麼方便**:手機不是一個「次等的遙控器」,它和你的終端機是**同一個工作階段的兩個視窗**。0 次重述上下文。

**驗收**:手機交辦 → 電腦 `codex resume` → 追問「剛剛那個檔」,它答得出來。

### 3.6 搞砸的時候

**痛**:誤發、發錯、跑歪了、它開始做你沒要它做的事。

**設計**
- **最壞情況被上限鎖死**:不管交辦內容多離譜,它**出不了 `D:\AgentHub`**(§6.1 硬牆),也**跑不了黑名單指令**(§6.2)。所以誤發的損害有明確天花板——這是「敢隨手交辦」的真正來源。
- **預設 read-only**,誤發的最壞後果是「浪費幾秒讀了些檔」。
- 要寫入得 `!tb unlock 30`(時限)。**時限會自己到期回到安全狀態**——你忘記 lock 不會變成長期風險。注意 `unlock` **只開放 AgentHub 內的寫入,不會擴大路徑範圍**。
- 跑歪了:執行中直接送純文字 = `turn/steer` 併入當前輪,不用先 stop 再重下。
- 停:`!tb stop`(收尾停)/ `!tb kill`(硬停)。
- 沒登入 Codex 時**不要靜默失敗**,直接說「Codex 未登入」並給 `!tb login`。→ **§7 R6**

**為什麼方便**:錯誤的代價被設計成很低,所以你敢隨手交辦——**敢用**才是便利的前提。

**驗收**:任何誤發在 read-only 下都不會改到檔案;`unlock` 到期自動回 read-only;**針對 AgentHub 外路徑的存取嘗試(含 `..`、UNC、symlink 繞道)全部被拒且留下稽核**。

> **狀態欄定義(評審要求)**:✅ = 有對應綠燈測試或 commit;**引擎存在** = 底層方法有,但指令層未接線,使用者打不出來;🔜 = 未做。凡標 ✅ 未附證據者一律降級。

| 你會打的 | 意思 | 狀態 |

| `!tb <一句話>` | 交辦,預設 AgentHub | ✅ |

## 5. 推播預算(一頁講完什麼時候會吵你)

每輪任務目標:**常態 1 次**(只有「完成」)。加上 §6 名單制之後,批准那次在一般開發任務裡不會發生,**≤2 次**是最壞情況而非常態。

| 事件 | 送法 | 推播? |
|---|---|---|
| 收到交辦 → `⏳ 已收到` | 新訊息 | 你剛發完,人在螢幕前,不算成本 |
| 進度更新(可能數十次) | **編輯同一則** | **否** ← 整份設計的關鍵 |
| 心跳時間戳 | **編輯同一則** | **否** |
| 指令命中**白名單**直接跑 | **編輯同一則** | **否** ← §6.3 買到的安靜 |
| 指令命中**黑名單/路徑越界**被拒 | **編輯同一則**(寫明拒絕原因) | **否**(不必問你,所以也不必吵你) |
| 需要你批准(僅**灰區**) | **新訊息** | **是**(少數情況才發生) |
| 完成 / 失敗 | **新訊息** | **是**(常態唯一一次) |
| 卡住警告(>N 分鐘) | 編輯 + **一次**新訊息 | 是(例外,值得) |

## 6. 安全模型:兩道硬牆 + 一組名單(而不是一直問你)

**設計出發點是便利,不是防禦。** 批准疲勞是真實的失敗模式:問太多次,人就會閉著眼按 `ok`,那等於沒有安全。所以把「絕對不行」做成**硬牆**、「絕對可以」做成**白名單**,剩下要問的才會少到你願意認真看。

判斷順序(先命中先決定,**不往下走**):

```
① 路徑硬牆    → 碰到 AgentHub 外 ──────────► 拒絕,不問(連你都不能批准)
② 指令黑名單  → 命中 ──────────────────────► 拒絕,不問
③ 指令白名單  → 命中 ──────────────────────► 直接執行,不打擾
④ 以上皆非(灰區) ─────────────────────────► 才問你(§3.3)
```

### 6.1 硬牆一:路徑(不可批准)

**任何讀取或寫入,只要目標落在指定資料夾外,一律違規、直接拒絕。** 指定資料夾預設為 `D:\AgentHub`。

- 這**不是**批准題。即使是 owner 本人也不能當場放行——要擴大範圍只能改設定並重啟,不能在對話中被說服。
- 涵蓋繞道寫法:`..` 相對路徑跳脫、絕對路徑、UNC(`\\server\share`)、symlink/junction 指向外部、`%USERPROFILE%` 之類環境變數展開後越界。一律以**解析後的真實路徑**判定。
- 為什麼這樣更好用:這是唯一能讓你**敢隨手交辦**的保證。你不必在批准當下自己判斷「這個路徑安不安全」——那本來就不該是手機上做的事。
- `unlock` 只切換「AgentHub **之內**能不能寫」,**永遠不擴大路徑範圍**。

> **歸屬釐清(評審核實,重要)**:這道牆的**執行者是 Codex sandbox**(`writableRoots` / read-only),**不是 TeamBot**。CDP+app-server 架構下 TeamBot 看不到 Codex 每一次檔案讀寫,無法自己在寫入前攔截。因此:
> - PRD **不承諾** TeamBot 自建路徑牆;`guards.ts` 的 `isPathAllowed` 只是**靜態字串前置檢查**(且 realpath 尚未實作,§0.5)。
> - 「繞道全部被拒」的真正被測物是 **Codex sandbox**。必須對它做 `..`/UNC/junction/`%VAR%` 繞道實測(CI 實建 junction 指向 `C:\` 驗證被拒),**拿到證據前 §8/§9 的「AgentHub 外存取=0」不得宣稱**。

### 6.2 縱深防禦:指令黑名單(升級為必問/隔離,**不是不可繞的牆**)

命中即**升級處理**——高危險樣式不當灰區小事帶過。但評審明確定調:**黑名單靠 regex 字串比對,天生可被繞過**(`cmd /c`、PowerShell `-EncodedCommand`、base64、變數拼接、別名、反引號、換行),所以它是**縱深防禦的一層提示**,不是安全天花板。

- 真正的結構性天花板是 **§6.1 路徑牆 + 預設 read-only + `networkAccess=false`**——這幾個不靠字串比對。
- 因此黑名單命中時的動作是「**升級為必問 / 隔離**」而非「宣稱一定攔住」;§9 威脅表與測試命名**不得**寫成「黑名單=可靠攔截」。
- 機密防護**不靠指令命名**:改成「讀取來源路徑落在 AgentHub 外即拒」(與 §6.1 合流),而非比對 `.ssh`/`GH_TOKEN` 字串(改個變數名就繞過)。

| 類別 | 例(樣式比對,非窮舉) |
|---|---|
| 破壞性刪除/格式化 | `rm -rf`、`del /s /q`、`Remove-Item -Recurse -Force`、`format`、`diskpart` |
| Git 歷史改寫 | `push --force`、`reset --hard`、`clean -xfd`、`filter-branch` |
| 提權 | `sudo`、`runas`、`Start-Process -Verb RunAs`、`net user`、`takeown`、`fsutil` |
| 機密外洩 | **以來源路徑判定**(讀 AgentHub 外的 `.ssh`/`.pem`/`.env`/`credentials`/`GH_TOKEN`) |
| 下載即執行 | `curl … \| bash`、`iwr … \| iex`、`Invoke-Expression`、`certutil -decode` |
| 削弱防護 | 關閉 Defender/防火牆、改安全性 registry、`Set-ExecutionPolicy Unrestricted` |
| 對外網路 | 預設整個沙箱 `networkAccess = false` |

### 6.3 白名單:日常指令直接跑(0 打擾)

| 類別 | 例 |
|---|---|
| 讀取/檢視 | `ls`、`dir`、`type`、`cat`、`git status`、`git diff`、`git log` |
| 建置測試 | `npm test`、`npm run <script>`、`npm ci`、`node`、`tsc`、`dotnet build`、`dotnet test` |
| 本地版控 | `git add`、`git commit`、`git checkout -b`、`git stash` |
| 檔案編輯 | AgentHub **之內**的建立/改寫(已受 §6.1 保護) |

- 白名單是 **per-project** 的(資料模型從第一天以 `projectId` 為鍵,即使目前恆為 AgentHub 單值,避免日後長回多專案要 migration),可由 `ok 永遠` 逐步長出來(§3.3)→ 打擾隨時間遞減。
- 白名單**不能覆蓋硬牆**:`git commit` 在白名單上,但若它要寫的檔在 AgentHub 外,仍然被 §6.1 拒絕。判斷順序在程式裡必須先跑 ①②再 ③(需單元測試鎖定)。
- **樣式必須精確**(評審):禁止萬用 `npm run <任意>`(等於一次批准打開一整類,含惡意 script 呼叫外部工具),須具名 script。
- **條目給 TTL**(如 30 天):到期前**主動在聊天問一句是否保留**,而非靜默失效(靜默失效會造成「以為還放行卻突然被擋」的困惑)。
- `ok 永遠` 執行時**就地回顯**「已加入樣式:`<具體 pattern>`」,不默默吸收;`!tb 名單` 要一眼看懂每條是什麼、上次命中時間。

### 6.4 其餘不可退讓

永不自動批准(灰區逾時 → 拒絕);`kill` 隨時可用;`unlock` 有時限且到期自動回 read-only;對外訊息與日誌去識別(token/cookie/env);owner 以不可變 sender id 授權;附加式稽核記錄每一次「拒絕/放行/加白名單」。

> ⚠️ **稽核尚未實作**(§0.5):全 repo 無 audit 表、無寫入,連 schema 都不存在。上述「附加式稽核」是需求不是現況。稽核列為與硬牆同批的**出貨前置**:append-only(禁 UPDATE/DELETE)、記錄 `{時間, senderId, 對話, 指令原文去識別, 決策 deny/allow/whitelist-add, 命中規則}`,每個 deny/allow/whitelist 路徑補測試確保寫入且不可竄改。

### 6.5 與現有實作的落差(評審核實)

| # | 落差 | 現況 | 需求 |
|---|---|---|---|
| 1 | 危險指令分類 | `guards.ts` 是 **always-approve(一律要問)** | 改成 §6.2 的「命中即升級必問/隔離」+ 補齊缺漏樣式(`diskpart`/`Set-ExecutionPolicy`/`takeown`/`fsutil`/`wmic`/`certutil -decode`),每類寫正例+對抗性負例 |

這是行為變更,見 §7 **R7**(拆為可獨立驗收子項)。
